# Décisions de la phase 0

Ce document tranche les hypothèses marquées **[À VÉRIFIER]** de la spec (§0 à §20), consigne les écarts par rapport à la spec avec leur raison, et liste les questions qui restent ouvertes pour l'utilisateur. Les réponses détaillées sont dans [`vanilla-reference.md`](vanilla-reference.md) (partie A : analyse statique du code décompilé de Valheim 1.0.17 ; partie B : données d'exécution du dump `mw_dump` sur Valheim 1.0.20, brutes dans `vanilla-reference-dump.md`). Les versions épinglées sont dans [`versions.md`](versions.md).

Légende des statuts :

- **tranché (analyse statique)** : le code décompilé suffit à répondre.
- **partiellement tranché** : le code répond à une partie, le reste dépend des données de prefab ou d'un essai en jeu.
- **tranché (dump 1.0.20)** : le dump d'exécution (`vanilla-reference-dump.md`, Valheim 1.0.20, 2026-10-24) répond ; les lignes `L..` renvoient à ce fichier.
- **à confirmer à l'exécution (mw_dump)** : la réponse n'existe que dans les données des prefabs chargés ; la ligne correspondante de la partie B de `vanilla-reference.md` (sections B.1 à B.9) liste ce que le dump doit produire.
- **sans objet (méta)** : la balise figure dans une phrase de méthode ou de plan, pas dans une hypothèse sur le jeu.

Les références `A.n` / `B.n` renvoient aux sections de `vanilla-reference.md` ; les `Fichier.cs:ligne` renvoient à `reference/decompiled/assembly_valheim/`.

### 1.3 Corrections de la spec découvertes par l'analyse statique

Ces points ne sont pas des balises mais contredisent ou précisent la spec ; ils sont à reporter dans la spec à l'occasion de la prochaine révision.

- `HitData.DamageModifier` compte **neuf** valeurs (Normal, Resistant, Weak, Immune, Ignore, VeryResistant, VeryWeak, SlightlyResistant, SlightlyWeak ; multiplicateurs 1 ; 0,5 ; 1,5 ; 0 ; 0 ; 0,25 ; 2 ; 0,75 ; 1,25), la spec §3.2 en cite sept (A.2).
- Spec §6.4 : « blocage parfait (Call to Arms) -> coup annulé » est inexact en 1.0 : une parade parfaite multiplie la puissance de blocage par `m_timedBlockBonus` mais **n'annule pas** le coup (reste `clamp01(dmg/(4 ac)) x dmg`, faible mais jamais nul) ; elle coûte moins d'endurance et peut étourdir l'attaquant seulement si celui-ci est un `Character` (A.3). Le test d'acceptation de la parade doit en tenir compte.
- `HitData.m_dodgeable` et `m_blockable` sont `false` par défaut : une morsure doit les poser à `true` si on veut qu'elle soit bloquée (spec §6.4) ou esquivée. Les images d'invincibilité de roulade annulent le coup avant le blocage (A.1, A.2).
- Un `Character.Awake` relance `SetupMaxHealth()` pour un non-joueur propriétaire à pleine santé : un `s_maxHealth` personnalisé de l'amas est écrasé à chaque réinstanciation. Le PV de l'amas doit être réimposé après `Awake` (A.5).
- `EnemyHud` n'affiche la barre d'une créature ordinaire qu'après un survol du viseur (60 s ensuite) ; `GetBaseAI()` y est appelé sans test (A.21).
- `Humanoid` est requis par `MonsterAI` (A.15), donc par l'amas.
- `ZRoutedRpc` ne sait pas sérialiser `byte[]` (ignoré en silence) ; un serveur qui rencontre un hash de prefab inconnu **détruit** la ZDO : les prefabs du mod doivent être enregistrés avant la première zone chargée (A.25).
- `Game.UpdatePause()` réécrit `Time.timeScale` à chaque frame : le harnais utilise `Game.FadeTimeScale` (A.29).

## 2. Écarts et choix

Écarts et décisions du 2026-10-24, chacun avec sa raison.

1. **Python 3.11.7 accepté au lieu de 3.12** (spec §1.1). `tools/vh.py` n'utilise que la bibliothèque standard ; aucune fonction propre à 3.12 n'est nécessaire.
2. **ilspycmd épinglé à 9.1.0.7988.** Les versions 10.x et 11.x exigent .NET 10 et ne s'installent pas sur les SDK 8/9 de la machine.
3. **Le `dotnet` du PATH est un hôte x86 sans SDK.** Les scripts appellent explicitement `C:\Program Files\dotnet\dotnet.exe` (x64), et `global.json` à la racine épingle le SDK 8 (`8.0.426`, `rollForward: latestFeature`) comme le demande le §1.1 de la spec. Le SDK 9.0.103 est aussi installé ; `global.json` empêche qu'il soit choisi.
4. **BepInExPack_Valheim 5.4.2351 épinglé**, alors que Jötunn 2.30.2 déclare 5.4.2333 : le pack est plus récent et compatible (même branche 5.4.x).
5. **Jötunn référencé depuis la DLL Thunderstore**, copiée dans `reference/game-dlls`, plutôt que depuis le paquet NuGet `JotunnLib` : c'est exactement le binaire qui sera chargé en jeu avec le mod, et il évite une deuxième source de version.
6. **Le plugin « dump » de la phase 0 est implémenté comme commande de dev** `mw_dump` / `POST /dump` dans le build Debug (`src/MistWorms/Dev/VanillaDump.cs`), et non comme plugin temporaire séparé. Il est exclu de la Release automatiquement (`#if MW_DEV`), ce qui évite un second projet à maintenir et à supprimer.
7. **Blender épinglé à 4.5.5 LTS** : winget propose des versions 5.x, la spec demande 4.x.
8. **La racine du dépôt est le dossier qui contient la spec** : pas de sous-dossier `mistworms/` (§1.4 de la spec).
9. **`steam_appid.txt` écrit dans `C:\ValheimDev`** pour que la copie du jeu démarre en dehors de la bibliothèque Steam.
10. **SteamCMD demande un lancement d'initialisation** avant `app_update` : le premier lancement ne fait que se mettre à jour et ignore les commandes suivantes. `tools/setup-server.ps1` lance donc `steamcmd +quit` seul d'abord, puis tolère le code de sortie 7 en vérifiant la présence de `valheim_server.exe`.
11. **Texte français de l'équipement : trait d'union ASCII** `Équipement -{0}` au lieu du signe moins U+2212 de la spec, car les polices de Valheim peuvent ne pas contenir ce glyphe. À vérifier visuellement en phase 5.
12. **La section de config `Dev` est liée dans tous les builds**, pour que les clés ne soient jamais nulles ; elle apparaît donc dans le `default.cfg` de la Release. Sans effet hors du build Debug (le code de dev est sous `#if MW_DEV`).
13. **Le projet de tests référence les DLL du jeu non publicisées**, donc les tests ne doivent pas toucher aux membres privés du jeu ; seule la logique pure du mod est testée hors jeu.
